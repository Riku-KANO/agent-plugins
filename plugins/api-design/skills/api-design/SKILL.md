# api-design

API の境界（HTTP / RPC / ストリーミング）を設計・レビュー・進化させるときに、原則とトレードオフを揃えて議論を進めるためのスキル。

このスキルが扱うのは「**設計の意思決定**」であって、コード生成やスキーマファイル自動生成は対象外。たとえば「`POST /users` を作るコードを書いて」だけならスキルを起こすほどではない。一方「ユーザー周りの API をゼロから切りたい」「この OpenAPI をレビューして」「v2 で破壊的変更を入れる、移行戦略は」は中心ユースケース。

## 最初にやること: モードを判定する

ユーザーの依頼を 3 つの**モード**のいずれかに分類してから動く。判定を誤ると出力フォーマットが全部ずれるので最初に決める。

| モード | 判定の手がかり | 出力の中心 |
|---|---|---|
| `new-design` | 「ゼロから」「新しく」「ユーザー機能の API を作る」「リソース設計」 | リソース/操作の一覧と根拠 |
| `review` | 既存の spec/コード/ドキュメントを示して「見てほしい」「問題ある?」 | 重大度付きの指摘リスト |
| `versioning` | 「v2」「破壊的変更」「移行」「deprecate」「後方互換」 | 変更分類と移行パス |

複合（例: 既存をレビューしつつ v2 を設計）の場合は明示的に「review パート → new-design パート」と段を分ける。

## 次にやること: API スタイルを確定する

ユーザーが既にスタイルを指定していればそれに従う。指定がない場合、以下の決定木で**短く**確認してから進む（黙って一つに決め打たない — スタイル選定は後で覆ると手戻りが大きい）。

- 公開 API、ブラウザ/サードパーティ向け、CDN/キャッシュ親和性重要 → **REST**
- フロントエンドが必要なフィールドを選びたい / 集約 query が多い → **GraphQL**
- 社内マイクロサービス間、強い型、双方向ストリーミング、低レイテンシ → **gRPC**
- サーバー → クライアント push、長時間接続、進捗/通知 → **WebSocket / SSE**

スタイルが決まったら、対応する `references/*.md` を読み込む（後述の「参照ファイル」セクション参照）。

## 次にやること: コンテキストを集める

設計判断のほぼ全てはコンテキスト依存。最低限以下を聞く（ユーザーが既に伝えていれば省略）:

1. **コンシューマー**: 誰が呼ぶ? 自社フロント / 他チーム / 外部開発者 / モバイル
2. **規模**: 想定 RPS / データ量 / 同時接続数のオーダー
3. **データの寿命**: 強整合性が必要か / 結果整合で OK か
4. **認証境界**: パブリック / 認証済みユーザー / サービス間 / 管理者
5. **既存資産**: 既存 API との一貫性をどこまで保つか
6. **運用制約**: SLA、レイテンシ目標、デプロイ頻度、可逆性

聞きすぎても進まないので、最初は 2–3 個に絞り、設計案の中で「仮定: X と置いた」と明示する手も使う。

## 設計を組み立てる: 普遍的な原則

スタイルを問わず必ず通すべき原則。出力前にこのチェックを内省的に回す。

### 1. 一貫性 (consistency)

- **命名規則を 1 つ決めて全体に適用**する。REST は **URL パスを kebab-case** に統一（複数語は `/user-profiles`、`/order-items`、`/api-keys`）。JSON ボディのフィールド名は別の決定で snake_case か camelCase を選び、その中で揃える。GraphQL は camelCase が慣習、gRPC は snake_case フィールド + PascalCase メッセージ。
- 似た概念には似た形を与える。`get_users` / `list_users` / `users.list` を混在させない。
- ステータスコード / エラーコード / ID 形式（UUID か数値か）も一貫させる。

### 2. 予測可能性 (predictability)

- 同じ動詞は同じ意味で使う。REST の `POST` が片方で create、もう片方で「アクション実行」になっていたら立ち止まる。
- レスポンス構造に「サプライズ」を入れない。リスト系は常に `{items, page_info}` 形、単体取得は常にトップレベルにオブジェクト、といった形を統一。

### 3. リソース/エンティティのモデリング

- 名詞で考える（REST: コレクション/アイテム、GraphQL: 型、gRPC: メッセージ）。
- 「動詞をリソースにする誘惑」を避けつつ、避けがたい場合（`/users/{id}/activate` や RPC 風アクション）は **理由を明文化**して例外として扱う。
- 1 リソースに過剰なフィールドを詰めない。集約 vs 分離の判断は「同じトランザクションで読み書きされる単位か」を基準に。

### 4. エラーモデル (error model)

- **機械可読なコード** + **人間向けメッセージ** + **トレース ID** の 3 点セット。
- HTTP ステータスは粗い分類だけ（4xx = クライアント起因、5xx = サーバー起因）。詳細はボディの error code で表現。
- `{"error": {"code": "USER_NOT_FOUND", "message": "...", "request_id": "..."}}` のような明示構造。
- どんなエラーがどんな条件で返るかを各エンドポイントごとに列挙する（呼び出し側のリトライ判断に必要）。

### 5. 冪等性 (idempotency)

- `GET` / `PUT` / `DELETE` は本質的に冪等。`POST` は冪等でない → 必要なら **Idempotency-Key ヘッダ** を受け入れる。
- 「2 回呼んだら 2 件作られる」が許容できないユースケース（決済、注文作成）は冪等性キーを必須に。
- gRPC でも同様: リトライ可能な RPC かどうかを各 method に明示。

### 6. ページネーション

- **カーソル方式を第一選択**にする（offset/limit は大規模データで破綻し、項目追加で重複/欠落が起きる）。
- レスポンスに `next_cursor` / `has_more` を返す。`total` は重い場合は省略可。
- 詳細は `references/rest.md` の pagination セクション参照。

### 7. フィルタ / 並び替え / 部分取得

- 用途が予測できる範囲だけサポートし、任意 SQL 風クエリは避ける（攻撃面 / インデックス計画 / 後方互換性が崩壊する）。
- GraphQL の場合は逆に「クライアントに選ばせる」が主役 → `references/graphql.md` 参照。

### 8. 認証 / 認可境界

- 認証（誰か）と認可（何ができるか）を分けて設計する。
- リソース単位の認可（テナント分離、所有権チェック）を「全エンドポイント横断のミドルウェア」で**漏れなく**かけられる構造に。
- 公開 API ならスコープ / API キー / OAuth スコープの設計を最初に固める（後付けは破壊的変更になる）。

### 9. スロットリング / レート制限 / バックプレッシャ

- 「**負荷が想定を超えたとき何が起きるか**」を仕様上必ず明示する。設計し忘れると、ある呼び出し元の暴走が全体を巻き込む。
- 設計対象は 2 層:
  - **サーバー側の制限**: rate limiting（per user/IP/key/endpoint）、コスト重み付け、ハード/ソフト、tier 分け
  - **クライアント側の引き**: exponential back-off + jitter、`Retry-After` 尊重、circuit breaker、リトライ対象/非対象の規律
- 最低限の標準:
  - `X-RateLimit-Limit` / `Remaining` / `Reset` を**毎レスポンス**に載せる（超過時だけではない）
  - 超過時は 429 + `Retry-After`、システム全体の負荷起因は 503 + `Retry-After` と意味を分ける
  - 重い操作（検索、AI 呼び出し、エクスポート）は**コスト重み付け**で別バケット
- バックプレッシャ層: load shedding、circuit breaker、queueing/async 化、bulkhead でテナント間隔離。
- 詳細は `references/throttling.md` を参照（アルゴリズム選定、分散実装、ストリーミング系の引き、アンチパターン含む）。

### 10. バージョニング姿勢

- **後方互換が破壊的変更より遥かに優先**。フィールド追加・新エンドポイント追加は破壊的でない。
- 既存フィールドの意味変更・必須化・削除は破壊的 → 別 version を切るか、新フィールド追加 + 古いものを deprecate する道を検討。
- 詳細は `references/versioning.md`。

### 11. 観測可能性 (observability)

- リクエスト ID（クライアントが渡せる + サーバーが採番して返す）。
- ログ / メトリクス / トレースに API 操作名が乗る設計（GraphQL なら operation name 必須、REST ならルートパターンが粒度）。

### 12. セキュリティ初期設定

- 入力検証は境界で完結させる（型・長さ・enum・正規表現）。
- 機密データ（PII、トークン、秘密鍵）はレスポンスに含めない / マスクするのがデフォルト。
- CORS / CSRF / Auth ヘッダの扱いは公開 API 設計の初期に決める。

## 出力フォーマット

モードごとに以下の形に揃える。Markdown で構造化して返し、思考の流れだけのテキストにしない。

### `new-design` モード

```markdown
## 1. 問題設定とスコープ
（誰のための API か、解く問題、スコープ外）

## 2. 主要リソース / エンティティ
（名前 / 意味 / 主なフィールド / 関連）

## 3. 操作一覧
（REST: パス・動詞・概要 / GraphQL: query/mutation/subscription / gRPC: rpc 一覧）
表形式が読みやすい。

## 4. エラーモデル
（コード一覧と発生条件）

## 5. 認証 / 認可
（誰がどの操作を呼べるか、スコープ設計）

## 6. バージョニング姿勢
（initial version、後方互換戦略）

## 7. 仮定と未決事項
（コンテキスト不足で仮定したこと、ユーザーに確認したいこと）
```

### `review` モード

各指摘に **重大度** を付ける。

- `critical`: 後方互換を壊す / セキュリティ問題 / 仕様矛盾
- `warning`: ベストプラクティス違反だが動く
- `nit`: スタイル・命名の好み

指摘形式:

```markdown
### [critical] エンドポイント命名で動詞を使っている
- 該当: `POST /createUser`
- 問題: REST 規約はリソース指向。`POST /users` にすべき。
- 影響: 新規エンドポイントが追加されるたびに一貫性が崩れる。
- 推奨修正: `POST /users` に変更し、既存呼び出しを deprecation 期間付きで誘導。
```

スパムにならないように、本当に意味のある指摘だけ出す。**「指摘 0 件」も完全に有効な結論**。

### `versioning` モード

```markdown
## 1. 変更分類
| 変更 | 種別 | 理由 |
|---|---|---|
| フィールド `email` を必須に | breaking | 既存クライアントが送らない可能性 |
| `phone_number` フィールド追加 | additive | 既存は無視するだけ |

## 2. 推奨アプローチ
（別 version を切る / additive で逃げる / 拡張点を使う、の選択肢と理由）

## 3. 移行パス
（deprecation 期間、移行手順、ロールバック方針）

## 4. リスクと前提
```

## やってはいけないこと

- **スタイル選定をユーザーの意向確認なしに決め打つ**。「REST が標準だから REST」とせず、コンテキストから合理性を述べた上で確認。
- **「あらゆるケースに対応できる API」を目指す**。汎用性のために YAGNI を破ると、結局誰の役にも立たないものになる。最初のコンシューマーで一度コミットしてから広げる。
- **巨大なスキーマや OpenAPI を一気に生成して返す**。原則と意思決定の根拠が伝わらない。まず構造・操作リスト・根拠 → ユーザー合意後に詳細、の順で。
- **コード生成に流れる**。このスキルは設計議論。実装に落とす段はユーザーが明示的に「コードに落として」と言ってから。

## このスキルを使わない / 軽く流すケース

- 既に十分に詳細な設計があり、純粋にコードへの落とし込みだけが残っているとき
- 単一エンドポイントの 1 行修正など、原則レベルの議論が過剰なとき
- ユーザーが「とにかく動くものをサッと」と明言しているとき（簡素な提案で十分）

その場合でも、明らかな原則違反（破壊的変更を無自覚に入れている、認可が抜けている等）に気づいたら短く警告する。
