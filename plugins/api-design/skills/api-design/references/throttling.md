# スロットリング / レート制限 / バックプレッシャ設計

API の「**負荷が想定を超えたとき何が起きるか**」を事前に設計する。これを怠ると、一部の重い呼び出し元が全体を巻き込んで落とすか、SLA をひっそり破る運用に陥る。

設計対象は 2 層に分かれる:

- **サーバー側の制限 (rate limiting / throttling / quota)**: 「うちはここまでしか受けない」を明示するメカニズム
- **クライアント側の引き (back-off / circuit breaker)**: 「断られたら / 詰まったら、どう退く」のプロトコル

両者は仕様で**ペアで定義**する。サーバーが 429 を返しても、クライアントが何も読まずに即リトライしたら何も解決しない。

## なぜ必要か

- **公平性**: 1 利用者が他利用者の応答性を奪わない
- **保護**: 下流の DB / 外部 API の過負荷を上流で吸収する
- **コスト**: 課金システムや AI 推論など「呼ぶたびにお金が出る」依存先を守る
- **DoS 耐性**: 悪意・事故問わず暴走を吸収する
- **予測可能性**: 利用者が「自分はどこまで叩いていいか」を知れる

## 制限ディメンジョン (何で区切るか)

複数を組み合わせるのが普通。

| ディメンジョン | 例 |
|---|---|
| 認証主体 | API キー / ユーザー / アプリケーション |
| ネットワーク | IP / IP レンジ / リージョン |
| エンドポイント | パス単位 / メソッド単位 |
| 操作コスト | "1 リクエスト = N コスト" として重み付け |
| 時間窓 | 秒 / 分 / 時間 / 日 / 月 |
| プラン階層 | free / pro / enterprise |

設計時に「**少なくとも以下は分ける**」が出発点:

1. 認証なし vs 認証あり（未認証は厳しめ）
2. 読み取り vs 書き込み（書き込みは厳しめ、または別バケット）
3. 「重い」操作（検索、集計、エクスポート、AI 呼び出し）は別バケット

## アルゴリズムの選択

| アルゴリズム | 特徴 | 向く用途 |
|---|---|---|
| **Token Bucket** | 一定速度で補充、バーストを蓄積分まで許容 | 公開 API デフォルト。瞬間的スパイクに優しい |
| **Leaky Bucket** | 一定速度で流れる、超過は溢れる | 下流速度を保護したいキュー的用途 |
| **Fixed Window** | "1 分あたり N" を時計窓で数える | 実装単純。窓境界でバースト 2 倍が起こる |
| **Sliding Window Log** | 直近 N 秒の全リクエストを記録 | 正確だがメモリ消費大 |
| **Sliding Window Counter** | Fixed + 直前窓の按分 | 実用バランス。Redis 実装が定番 |

**第一選択は Token Bucket か Sliding Window Counter**。Fixed Window は単純だが境界バーストの説明が面倒で公開 API には不向き。

## コスト重み付け (cost-weighted)

「1 リクエスト = 1」で数えない。

```
GET /users/{id}            = 1 unit
GET /users?q=...&limit=100 = 5 units
POST /search/full-text     = 20 units
POST /reports/generate     = 100 units
```

- バケット容量を「units」で表現し、操作ごとにコストを乗せる
- ユーザーの「呼んだ回数」より「使ったリソース」が制限の意味として正しい
- ドキュメントで各エンドポイントのコストを公開する

## レスポンス設計

### 制限内のとき

通常レスポンスに **現状ヘッダ** を載せる（毎回返す）。

```
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 873
X-RateLimit-Reset: 1717689600
X-RateLimit-Resource: read
```

- `Limit`: 現在の窓の上限
- `Remaining`: 残り
- `Reset`: リセット時刻（UNIX time）or 残り秒（仕様で統一）
- `Resource`: バケットを複数持つなら識別子

新しめの規格として `RateLimit-Limit` / `RateLimit-Remaining` / `RateLimit-Reset` (RFC 9239 ドラフト系) もあるが、現実は `X-RateLimit-*` がデファクト。

### 超過したとき

```
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1717689630
Content-Type: application/json

{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "Rate limit exceeded. Retry after 30 seconds.",
    "request_id": "req_...",
    "details": {
      "limit": 1000,
      "window_seconds": 60,
      "retry_after_seconds": 30
    }
  }
}
```

- `Retry-After` は秒数 or HTTP-date。秒数推奨（タイムゾーン事故が起きない）
- error code は安定識別子で（`RATE_LIMIT_EXCEEDED`）
- どの制限に当たったか (`per_user` / `per_ip` / `per_endpoint`) を `details` で示せると親切

## ソフトリミット vs ハードリミット

- **ハード**: 超過したら即 429。シンプル。
- **ソフト**: 超過しても通すが警告ヘッダ (`X-RateLimit-Warning`) を載せる。一定割合超えたら 429。
- 顧客向け公開 API はハード。社内 API はソフトで運用後に閾値調整、が現実的。

## バーストとサスティン

- ユーザーは「平均レート」より「瞬間のバースト」で困る
- 設計例: 平均 60 req/min を許す = 1 req/sec、ただし瞬間バーストとして 30 req まで許容
- Token Bucket だと「容量 30、補充 1/sec」で自然に表現できる

## バックプレッシャ (サーバー側の応答減衰)

レート制限はまだ「個別ユーザーの帯域」の話。**システム全体が詰まっているとき** はもう一段の対策が要る。

### 1. Load shedding (負荷捨て)

- システム指標（CPU、queue length、p99 latency）が閾値を超えたら、一部リクエストを 503 で即返す
- 「全部少しずつ遅くなる」より「一部を完全に拒否する」方が全体スループットは守れる
- 503 + `Retry-After` で返す（429 ではない — 429 は「あなたの上限」、503 は「サーバー全体」の意味）

### 2. Circuit breaker (回路遮断)

- 下流サービスが連続失敗 → 一定時間そのサービスへの呼び出しを止める
- API 側は 503 + 上流に「依存先 X が一時停止中」と返す
- 復旧確認は half-open で少しずつ再試行

### 3. Queueing / 非同期化

- 重い処理は即時返さず job 化: `202 Accepted` + job ID
- ジョブ実行は内部 queue で速度を絞れる
- 同期 API は薄く保ち、重い計算は async に逃がす

### 4. Bulkhead (隔壁)

- ユーザー A の重い呼び出しがユーザー B を巻き込まないよう、テナント単位でスレッドプールや connection pool を分ける
- マルチテナント SaaS では事実上必須

## クライアント側の引き (back-off プロトコル)

サーバー設計と同じくらいクライアント実装の規律が大事。仕様/SDK で以下を明示する。

### Exponential back-off + jitter

```
attempt 1: wait 1s  × (1 ± 0.25)
attempt 2: wait 2s  × (1 ± 0.25)
attempt 3: wait 4s  × (1 ± 0.25)
attempt 4: wait 8s  × (1 ± 0.25)
...
max: 60s
```

- **ジッタは必須**。揃ったタイミングでリトライすると thundering herd が起きる
- `Retry-After` ヘッダがあればそれを優先（サーバーの方が正しい）

### リトライ対象の判定

| ステータス | リトライすべき? |
|---|---|
| 408 Request Timeout | ○ |
| 425 Too Early | ○ |
| 429 Too Many Requests | ○ (Retry-After 尊重) |
| 500 Internal Server Error | △ (冪等な場合のみ) |
| 502 / 503 / 504 | ○ |
| 4xx (上記以外) | × |

- POST など非冪等は `Idempotency-Key` がない限りリトライしない
- 最大試行回数と最大累積待ち時間の両方を切る

### Circuit breaker（クライアント側）

- 連続失敗が閾値を超えたら一定時間サーバー呼び出しを止める
- 「壊れているサーバーに殺到する」を防ぐ
- SDK レベルで実装されているのが望ましい

## 階層プラン (tier design)

公開 API ではほぼ必須。

```
free:        100 req/min, 1k req/day, no burst
starter:     1000 req/min, 100k req/day, burst 100
pro:         10k req/min, unlimited daily, burst 500
enterprise:  契約に応じて個別
```

- 階層変更は契約や認証メタデータから決定 (`X-Plan` ヘッダや claims)
- 階層ごとの実利用量を観測してプラン設計を継続調整

## 内部 / 管理用のバイパス

- 監視・ヘルスチェック・admin tooling は通常制限の影響を受けないルートが必要
- ただし「ヘッダ付ければ無制限」のような雑な穴を作るとセキュリティ事故に直結
- 内部経路は別ネットワークやサービス間認証で隔離する

## 分散環境での実装注意

- 単一プロセス内のカウンタでは横スケールできない
- Redis (atomic INCR + EXPIRE) や DynamoDB conditional update が定番
- ノードローカル + 中央集約のハイブリッド (ノードで毎リクエスト集計せず数 ms バッチで Redis に集約) が高 RPS では現実解
- カウンタストアが落ちたとき "fail open" (全通) か "fail closed" (全拒否) かを設計上明示する

## 観測

レート制限は「黙って起きている異常」になりやすい。

- 429 / 503 の発生率を SLA ダッシュボードに出す
- 「どのユーザー / API キー / エンドポイントで詰まっているか」を切れる粒度で記録
- 上位 N の利用者の利用量を可視化し、プラン適正化の根拠にする
- アラート: 特定ユーザーが連続して 429 を受けている = サポート起点

## ストリーミング / WebSocket 系の引き

リクエスト/レスポンス型と違う論点が出る:

- **接続数の上限** (per user, per IP, per app)
- **メッセージレート上限** (送信側 / 受信側ともに)
- **ペイロードサイズ上限**
- **idle timeout** (一定時間無活動で切断)
- バックプレッシャは「サーバー → クライアント」では送信キューサイズが詰まり始めたら drop or 切断、「クライアント → サーバー」では受信レートを下げて送信側に滞留させる
- 詳細は `references/streaming.md` も参照

## アンチパターン

- **黙って遅くする**: 制限超過時に応答だけ遅延 → クライアントは原因が分からず長時間待つ → リトライ祭り
- **タイムアウトとリトライの組み合わせを設計せずに公開**: クライアントが無限に再試行 = 自分でレート制限を破る攻撃をしてくる
- **`Retry-After` を返さない 429**: クライアントは即リトライ以外の手を持てない
- **コスト重みなし**: 安いエンドポイントと重いエンドポイントが同じ枠で扱われ、重い呼び出しが事実上やり放題になる
- **エンドポイント全体で 1 つの大きなバケット**: 一部呼び出し元の重いユースケースが全体を巻き込む
- **fail closed が止まれない**: レート制限ストア障害でサービス全体が 0% になる → 復旧シナリオも設計
- **「内部 API だから無制限」**: 内部の暴走は外部より破壊力が大きいことが多い

## レビュー時の重点チェック

- [ ] レート制限ヘッダが**毎レスポンス**に乗っているか（超過時のみではない）
- [ ] 429 に `Retry-After` がある
- [ ] 429 と 503 の使い分けが明確か（個別 vs 全体）
- [ ] 認証なし / 認証あり / プラン階層で別レート
- [ ] 読み取り / 書き込み / 重い計算で別バケット
- [ ] コスト重み付けが妥当か（または不要な場合に根拠あり）
- [ ] バースト許容と平均レートが分けて設計されているか
- [ ] 分散環境のレート制限ストアと fail open/closed 戦略
- [ ] ストリーミングなら接続数・メッセージレート・idle timeout
- [ ] 利用量と 429/503 が観測可能（ダッシュボード）
- [ ] クライアント SDK / ドキュメントに back-off + jitter 推奨が書かれている
- [ ] テナント分離（Bulkhead）が必要なシステムで考慮されているか
