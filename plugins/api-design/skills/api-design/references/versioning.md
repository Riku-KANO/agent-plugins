# API バージョニング / 破壊的変更 / Deprecation 戦略

公開 API も社内 API も「変えたくなる」のが必然。設計の初期にバージョニング姿勢を決めておかないと、後の互換性事故で開発スピードが急停止する。

## 出発点: 「破壊的変更」を正確に分類する

何が breaking で何が additive かを最初に揃える。

### 一般的に additive（互換）

- 新エンドポイント / 新リソース / 新フィールドの**追加**
- 新しい optional パラメータの追加
- 新しいエラーコードの追加（既存ハンドラが汎用デフォルトを持つ場合）
- enum 値の追加（クライアントが未知値を許容する設計の場合）
- パフォーマンス改善・内部実装変更

### 一般的に breaking（非互換）

- 既存フィールドの**削除** / 必須化 / 型変更 / 意味変更
- 既存エンドポイントの削除 / メソッド変更
- レスポンス構造の変更
- バリデーションルールの厳格化（今まで通っていた値が弾かれる）
- ステータスコードや error code の意味変更
- 認証/認可ルールの強化（公開 → 要認証など）

「クライアントが何もしなくても動き続けるか」が判断基準。

## 戦略 1: バージョンを切らない（進化的設計を貫く）

**第一選択**。GraphQL コミュニティはこの方向が強い。REST/gRPC でも近年は推奨。

ルール:

- 破壊的変更を**入れない**。どうしても必要なら新フィールド追加 + 旧フィールド deprecate。
- `deprecated_at` を仕様に明記し、最低 6 ヶ月（公開 API なら 12 ヶ月以上）の移行期間を取る。
- 観測で「旧フィールドを使う呼び出し元」を計測し、ゼロ化を確認してから削除。

利点:
- バージョン分岐コードが不要、運用が単純。
- クライアントの自然な追従に任せられる。

欠点:
- 抜本的な再設計ができない。
- フィールド名が歴史的事情で歪んでも変えにくい。

## 戦略 2: メジャーバージョンをパスで切る（`/v1`, `/v2`）

REST 公開 API の伝統的方法。

ルール:

- パス先頭で `/v1/...`, `/v2/...` と切る。
- v1 と v2 を**並行運用**する期間を設ける（最低 12 ヶ月推奨）。
- v2 リリースと同時に v1 を deprecated とアナウンスし、sunset 日を予告。

実装パターン:

- 内部ハンドラは共通化し、v1 layer と v2 layer で input/output 変換だけ差し替える。
- 完全に重複コードにすると保守不能。

利点:
- 抜本的な変更が可能。
- 移行をクライアントの都合に委ねられる。

欠点:
- 並行運用のコスト（ドキュメント、テスト、データモデル変換）。
- 「v1.5」「v3 のベータ」など中間バージョンの誘惑に負けると地獄。

## 戦略 3: ヘッダでバージョン指定

`Accept: application/vnd.example.v2+json` のような形。

- 利点: URL を汚さない、より RESTful（同じリソースに対する表現の選択）。
- 欠点: ブラウザから直接叩きづらい、CDN キャッシュキーが複雑、デバッグしづらい。
- 公開 API では URL パス方式の方が現実的。社内 API なら検討余地あり。

## 戦略 4: GraphQL の `@deprecated`

- スキーマで `@deprecated(reason: "Use newField instead")` を付与。
- スキーマ exploration ツール（GraphiQL 等）が deprecation を表示。
- バージョンを切らずに進化を続ける GraphQL の標準的アプローチ。

## 戦略 5: gRPC のパッケージバージョン

- `package com.example.users.v1;` のように proto パッケージにバージョンを含める。
- v2 を `com.example.users.v2` として並行運用。
- 大きく型が変わるなら別パッケージ、互換変更なら同パッケージ内で追加で済ます。

## Deprecation の進め方

```
[1] Announce
   - Changelog / docs / dashboard に "deprecated at YYYY-MM-DD" を明記
   - レスポンスに Deprecation ヘッダ追加（RFC 8594）
   - 移行ガイドを公開

[2] Observe
   - 該当エンドポイント/フィールドの利用ログを計測
   - 主要利用者に直接連絡（公開 API なら通知メール）

[3] Throttle (optional)
   - 一部時間帯で意図的に旧 API を停止（"Brownout"）→ 利用者に気付かせる
   - 公開 API でやる場合は事前通知必須

[4] Sunset
   - 完全に提供停止。410 Gone を返す
   - 廃止日は事前通告と一致させる
```

## クライアントへの優しさ

- レスポンスヘッダ:
  - `Deprecation: true`（または日付）
  - `Sunset: Wed, 11 Nov 2026 23:59:59 GMT`
  - `Link: <https://docs/migration>; rel="deprecation"`
- ボディに `warnings` フィールドを定義しておくと、ランタイムで利用者にメッセージを届けられる。

## 「うっかり破壊的変更」を防ぐ仕組み

- **OpenAPI / proto の差分検査**を CI に入れる（`oasdiff`, `buf breaking` 等）。
- レビュー時に「これ breaking?」のチェック項目を必須化。
- スキーマファースト開発（先にスキーマ変更 → コード）にすると差分検査が機能する。

## モードごとの出力ヒント

`versioning` モードでの返答は以下を含めると有用:

1. 変更ごとの分類（additive / breaking）と理由
2. 推奨戦略（バージョン切る / 進化的）
3. 並行運用期間と sunset の目安
4. 移行手順（クライアント側、サーバー側）
5. ロールバック計画（v2 でリグレッションが出たときどうするか）
6. 観測指標（deprecation 計測の方法）

「シンプルに v2 切れば良い」と即答せず、戦略選択肢を提示してユーザーが選べる形にする。

## 落とし穴

- **「マイナーバージョン」を切りすぎる**: v1.1, v1.2 と乱発するとクライアントが追えなくなる。互換変更は無印、非互換のみメジャーバージョンを上げる。
- **バージョン違いで挙動が微妙に違うが仕様未記述**: 必ず両バージョンで仕様を完全に書き残す。
- **deprecate するが期限を切らない**: 永遠に残る → 結局新旧両方の保守コストを払い続ける。期限を必ず公表する。
- **「内部 API だから雑でいい」と思って後悔**: 社内サービス境界も契約。むしろ呼び出し元が多くて壊しづらいケースが多い。
