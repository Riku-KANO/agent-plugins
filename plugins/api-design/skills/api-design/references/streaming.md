# WebSocket / SSE 設計リファレンス

「サーバーからクライアントへの push」が必要なケース向け。設計判断の難しさは HTTP リクエスト/レスポンス API より一段上がる。

## まず: WebSocket か SSE か

| 観点 | WebSocket | Server-Sent Events (SSE) |
|---|---|---|
| 通信方向 | 双方向 | サーバー → クライアント単方向 |
| プロトコル | 独自 (HTTP からアップグレード) | 通常の HTTP/1.1 over chunked |
| 自動再接続 | クライアント実装次第 | ブラウザ標準でビルトイン |
| プロキシ/ファイアウォール | やや弾かれやすい | 通常の HTTP として通る |
| バイナリ | ○ | ×（テキスト） |
| ブラウザサポート | 全モダン | 全モダン（IE 除く） |

**デフォルトは SSE**。クライアント → サーバーの逐次送信が本当に必要 → WebSocket、というのが妥当な判断順。

## 接続ライフサイクル

設計時に以下のイベントを明示しておく:

- **接続確立** (`onopen`): 認証はどこで、ハンドシェイク中に何を送るか
- **メッセージ受信** (`onmessage`): メッセージフォーマット（後述）
- **エラー** (`onerror`): 再接続するか中断するか
- **切断** (`onclose`): 意図的か、ネットワーク起因か、サーバー強制か

それぞれの状態遷移をドキュメント化する。「気づいたら切れていた」が一番のトラブル源。

## 認証

- WebSocket: アップグレードリクエスト時のヘッダで JWT/Cookie を渡す。クエリパラメータ ?token=... は URL ログに残るので避ける（やむを得ない場合のみ）。
- SSE: 普通の HTTP ヘッダで認証。
- 接続中の権限失効（トークン失効、停止等）を扱うため、サーバーから `auth_expired` イベントを送って切断する設計を入れる。

## 再接続戦略

- **指数バックオフ + ジッタ** がデファクト。1s → 2s → 4s → 8s → … + ランダム ±25%。
- SSE は `EventSource` がデフォルトで再接続するので、サーバーは `retry: 5000` ディレクティブで間隔を指定可能。
- **再接続時の状態復元**: 最後に受け取ったイベントの ID をクライアントが覚え、再接続時に送る → サーバーがそれ以降を再送。
  - SSE は `Last-Event-ID` ヘッダで自動。
  - WebSocket は独自に同等の仕組みを設計する。

## メッセージフォーマット

JSON が無難。**必ず type フィールド**で識別する。

```json
{ "type": "notification.created", "id": "evt_123", "ts": "2026-06-06T10:00:00Z", "payload": { ... } }
```

- `type`: ドット区切りの階層命名で拡張に強くする
- `id`: グローバル一意。再接続時の重複排除と Last-Event-ID 用
- `ts`: 発生時刻（ISO 8601 UTC）
- `payload`: 種別ごとのスキーマ

新しい `type` の追加は非破壊的、フィールド意味の変更は破壊的、と REST と同じ感覚。

## バックプレッシャ

- クライアントが捌けない速度でサーバーが送ると、TCP バッファが詰まり最悪 OOM。
- 設計上の対策:
  - 1 接続あたりのメッセージレート上限
  - 重要度の低い更新はクライアントの ACK を待ってから次を送る
  - 大量の小イベントはバッチング
- WebSocket では明示的な `ping`/`pong` でハングを検知し、無応答なら切断する設計を入れる。

## メッセージの順序 / 重複 / 欠落

- ネットワーク事情で順序逆転や欠落は起きうる。「順序が必要か」「欠落を許容するか」を最初に決める。
- 欠落不可: イベント ID をシーケンシャルにし、クライアントが gap を検知 → 再取得。
- 順序保証必要: サーバーで sequence number を振り、クライアントが順序通りに処理。
- 重複許容: クライアント側で `id` による idempotency を実装。

## スケーリング

- 1 サーバーに数万接続を保持するため、ロードバランサ・スティッキーセッション・コネクション数の上限設計が初期に必要。
- 複数サーバー間で event broadcast したいなら Redis Pub/Sub や Kafka を間に挟む。
- メモリ上の状態を持たず、再接続でいつでもリビルドできる構造を保つ。

## SSE の細部

```http
GET /events HTTP/1.1
Accept: text/event-stream
Cache-Control: no-cache
```

サーバーレスポンス:

```
event: notification.created
id: 123
data: {"payload": ...}

event: notification.read
id: 124
data: {"payload": ...}
```

- 空行でイベント区切り。
- `event:` がない場合はクライアント側で `message` イベントとして扱われる。
- プロキシによる buffering を切るため、`X-Accel-Buffering: no` (nginx) などの設定が必要なことがある。

## WebSocket サブプロトコル

- 接続時の `Sec-WebSocket-Protocol` ヘッダで `chat.v1` のような名前を渡し、サーバーが受諾。
- バージョン管理に使える（v1 と v2 を別 subprotocol として共存）。

## レビュー時の重点チェック

- [ ] そもそも WebSocket / SSE が本当に必要か（ポーリングや HTTP/2 push で済まないか）
- [ ] 認証方式が安全か（URL クエリにトークンを置いていないか）
- [ ] 再接続時の状態復元手段が設計されているか（Last-Event-ID 相当）
- [ ] メッセージに type と id が含まれているか
- [ ] 順序保証 / 欠落許容のポリシーが明文化されているか
- [ ] バックプレッシャ対策があるか
- [ ] 切断条件と再接続戦略がドキュメントにあるか
- [ ] スケーリング前提（複数サーバー間の broadcast）が考慮されているか
