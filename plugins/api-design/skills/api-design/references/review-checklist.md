# API レビュー チェックリスト

`review` モードで漏れを防ぐための網羅的リスト。全項目を機械的に並べるのではなく、**該当する重大な指摘だけ**を出力すること。「指摘 0 件」も完全に有効な結論。

## 0. レビュー対象のメタ情報

- [ ] 対象がはっきりしている（OpenAPI / proto / SDL / コード / 設計ドキュメント）
- [ ] スタイル（REST / GraphQL / gRPC / streaming）を識別済み
- [ ] バージョンとリリース状況（unreleased / beta / GA）を把握

## 1. 一貫性

- [ ] 命名規則が統一されている
  - REST の **URL パスは kebab-case**（`/user-profiles`、`/order-items`）— camelCase / snake_case / PascalCase の混在 NG
  - JSON ボディは snake_case または camelCase のいずれかで全体統一（URL パスとは独立の判断）
  - GraphQL は camelCase、gRPC は snake_case + PascalCase
- [ ] 似た操作に似た形（list 系の構造、エラーの形）
- [ ] ID 形式が統一されている（UUID/数値/ULID）
- [ ] 日付フォーマットが統一（ISO 8601 UTC 推奨）
- [ ] フィールド名の語彙が一致（`user_id` と `userId` と `uid` が混在していないか）

## 2. リソース / 操作モデル

- [ ] パス / メソッド名がリソース指向（不必要な動詞を含まない）
- [ ] CRUD 以外の操作が必要な場合に正当性が説明できる
- [ ] 過剰にネストされた階層がない（2 階層まで目安）
- [ ] 「1 リソースに何でも詰め込む」と「過剰な分離」のバランス

## 3. HTTP / gRPC 詳細

REST:
- [ ] ステータスコードと body の整合
- [ ] POST / PUT / PATCH の使い分けが正しい
- [ ] 201 で `Location` ヘッダを返している
- [ ] 204 で body が空

gRPC:
- [ ] フィールド番号の再利用なし
- [ ] enum の 0 値が `*_UNSPECIFIED`
- [ ] 時刻 / 金額の型が適切（float ではない）

GraphQL:
- [ ] null/non-null が意図通り
- [ ] mutation が input + payload 規約
- [ ] ページネーションが Connection 規約

## 4. エラーモデル

- [ ] error code が安定識別子（人間メッセージとは別）
- [ ] エラー一覧がエンドポイント単位でドキュメント化されている
- [ ] request_id / trace_id がレスポンスに含まれる
- [ ] スタックトレース / SQL / 内部パスが露出していない
- [ ] バリデーションエラーが構造化されている（フィールド単位）

## 5. 冪等性 / リトライ安全性

- [ ] GET / PUT / DELETE が真に冪等
- [ ] POST のうち冪等性が必要なものに Idempotency-Key を受ける仕組み
- [ ] 各 RPC / endpoint が「リトライ可能か」明示

## 6. ページネーション / フィルタ / ソート

- [ ] 大量データを返しうるエンドポイントにページネーション
- [ ] cursor 方式 / offset 方式の選択が一貫
- [ ] サポートする filter / sort フィールドが仕様で明示
- [ ] 任意 SQL クエリ風の柔軟性を導入していない（または安全策がある）

## 7. 認証 / 認可

- [ ] 認証方式が明確（Bearer / OAuth / API Key）
- [ ] スコープ設計（公開 API の場合）
- [ ] リソース所有権チェックの仕組み（テナント分離、マルチユーザー）
- [ ] 「認可漏れ」が起きにくい構造（ミドルウェアで横串、デフォルト deny）
- [ ] 機密情報がレスポンスに含まれない / マスクされる

## 8. スロットリング / レート制限 / バックプレッシャ

詳細・アンチパターンは `references/throttling.md`。

- [ ] レート制限ヘッダ (`X-RateLimit-*`) が**毎レスポンス**に載っている（超過時のみではない）
- [ ] 429 に `Retry-After` がある
- [ ] 429（個別ユーザー超過）と 503（システム全体過負荷）の使い分けが明確
- [ ] 認証あり / なし / プラン階層で別レート
- [ ] 読み取り / 書き込み / 重い計算（検索、AI、エクスポート）で別バケット
- [ ] コスト重み付けがある（または不要な根拠が明示）
- [ ] バースト許容と平均レートが分けて設計されているか
- [ ] ストリーミング系なら接続数 / メッセージレート / idle timeout の上限
- [ ] クライアント SDK / ドキュメントに back-off + jitter 戦略が書かれている
- [ ] レート制限ストア障害時の fail open / closed 戦略が決まっている
- [ ] 利用量と 429/503 発生を観測できる仕組み

## 9. バージョニング / 互換性

- [ ] バージョニング戦略が明文化されている
- [ ] 提案されている変更が breaking / additive のどちらか分類されている
- [ ] breaking change の場合 sunset 計画が示されている
- [ ] `Deprecation` / `Sunset` ヘッダ、`@deprecated` ディレクティブの使用
- [ ] フィールド削除時に proto の `reserved` 宣言（gRPC）

## 10. パフォーマンス / スケーラビリティ

- [ ] N+1 を起こしうるリゾルバ / クエリに対策
- [ ] 重い処理が同期 200 で返っていないか（202 + job が適切な場合）
- [ ] レスポンスの payload サイズが妥当（巨大ネスト構造でないか）
- [ ] GraphQL なら複雑度 / 深さ制限

## 11. 観測可能性

- [ ] リクエスト ID（クライアント生成 + サーバー採番）
- [ ] ログに API 操作名が乗る粒度
- [ ] エラーごとに分類可能なメトリクスが取れる構造

## 12. ドキュメント / DX

- [ ] OpenAPI / proto / SDL がコードと同期している
- [ ] エラーケース、認証、レート制限、ページネーションがドキュメント化
- [ ] サンプルリクエスト / レスポンスがある
- [ ] 「これは廃止予定」が見える

## 13. セキュリティ

- [ ] 入力バリデーション（型、長さ、enum、正規表現）が境界で完結
- [ ] CORS ポリシーが意図通り
- [ ] CSRF 対策（cookie 認証の場合）
- [ ] 機密フィールドのログ抑制
- [ ] 認可境界のテストカバレッジ

## 14. ストリーミング固有

- [ ] 再接続戦略（Last-Event-ID / 同等）
- [ ] メッセージに type + id
- [ ] 認証トークンの安全な引き渡し
- [ ] バックプレッシャ対策

## 指摘の重大度ルール

- **critical**: 後方互換破壊、セキュリティ問題、ステータスコード/エラーの意味矛盾、認可漏れ
- **warning**: ベストプラクティス違反だが現状動く（命名規則違反、冪等性なし、deprecation 計画なし等）
- **nit**: スタイルの好み・微小な改善余地

critical を warning に格下げしない。warning を critical に格上げしてユーザーを焦らせない。
